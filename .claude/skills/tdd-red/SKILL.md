# tdd-red

`docs/features/tag/scenarios-$ARGUMENTS.md`의 시나리오를 **실패하는 테스트**로 만든다. TDD의 Red 단계까지만 한다.

인자가 없거나 시나리오 파일이 없으면 그 사실을 알리고 멈춘다. 시나리오 파일을 추측해서 만들지 않는다(없으면 `/test-scenarios`를 먼저 쓰도록 안내한다).

## 절대 규칙

- **구현 코드를 작성하지 않는다.** 구현 파일의 함수 본문은 `throw new Error('not implemented')` 한 줄뿐이다. 조건문, 계산, 반환값, 상태 처리를 넣지 않는다.
- 이미 구현된 파일이 있으면 본문을 바꾸지 않는다. 대신 그 사실을 사용자에게 알리고, 새로 필요한 함수만 껍데기로 추가한다.
- Green(통과시키기)으로 넘어가지 않는다. 테스트가 통과하게 만드는 것은 이 스킬의 일이 아니다.

## 절차

### 1. 시나리오를 Vitest 테스트로 변환

- `scenarios-$ARGUMENTS.md`의 시나리오를 읽고 하나당 `it`을 하나 만든다. 시나리오가 빠지거나 합쳐지지 않게 한다.
- `[정상]` `[경계]` `[예외]`는 `describe`로 묶고, `it` 이름은 시나리오의 `함수명 should … when …` 문장을 그대로 쓴다.
- 테스트 파일은 대상 파일과 같은 폴더에 `이름.test.ts(x)`로 둔다. 기존 테스트 파일이 있으면 시나리오만 추가한다.
- `describe`, `it`, `expect`는 `vitest`에서 명시적으로 import한다(globals가 꺼져 있다).
- 기대값은 시나리오에 적힌 값과 에러 메시지를 그대로 쓴다. 시나리오에 없는 동작을 만들어 넣지 않는다.

### 2. 구현 파일은 껍데기만

- 테스트가 import하는 함수·컴포넌트가 없으면 시그니처(`scenarios` 문서의 입력/출력 타입)만 맞춰 만든다.
- 본문은 정확히 아래 한 줄이다.

```ts
throw new Error('not implemented')
```

- 컴포넌트라면 props 타입만 정의하고 본문은 같은 `throw`로 한다. 렌더 결과를 흉내 내지 않는다.
- 이 프로젝트 규칙을 따른다: 컴포넌트는 named export만(`export default` 금지), 파일 이름은 컴포넌트 PascalCase·나머지 camelCase, 파일은 200줄을 넘기지 않는다.

### 3. 구현 금지 재확인

실행 전에 만든 구현 파일을 훑어, 본문에 `throw new Error('not implemented')` 외의 로직이 없는지 확인한다.

### 4. 실행하고 Red를 확인

`npm test`는 watch 모드라 끝나지 않는다. 한 번만 실행한다.

```
npx vitest run <테스트 파일 경로>
```

결과를 두 종류로 구분해 판단한다.

- **Red (정상 실패)**: 실패 원인이 `not implemented`다. 이것이 목표다.
- **Broken (고장)**: `Cannot find module`, 문법 오류, 타입 오류, import 오류, 잘못된 셀렉터처럼 `not implemented`가 아닌 이유로 실패하거나 실행조차 안 된다. 이것은 실패로 치지 않는다.

Broken이 하나라도 있으면 원인을 고치고 다시 실행한다. 고칠 대상은 테스트 파일의 import, 경로, 껍데기의 export 같은 **배선**이다. 테스트를 통과시키려고 구현 로직을 쓰지 않는다.

모든 테스트가 `not implemented`로 실패할 때까지 반복한다. 다음 경우는 Red가 아니므로 사용자에게 알린다.

- 테스트가 **통과**한 경우: 이미 구현돼 있거나 테스트가 아무것도 검증하지 않는 것이다. 어느 쪽인지 확인한다.
- 일부만 `not implemented`이고 나머지는 다른 이유로 실패하는 경우.

### 5. React 컴포넌트 테스트 규칙

- 요소는 접근성 역할로 먼저 찾는다: `getByRole`(+ `name`) > `getByLabelText` > `getByText`. 다른 방법이 없을 때만 낮은 순위를 쓴다.
- 내부 state, 컴포넌트 인스턴스, 훅 반환값을 검사하지 않는다. 화면에 보이는 결과와 콜백 호출만 검증한다.
- 사용자 조작은 `@testing-library/user-event`를 쓴다.
- `data-testid`는 최후의 수단이다.

## 보고

가장 마지막 줄에, 한눈에 잘됐는지 볼 수 있는 한 줄 요약을 출력한다. 형식은 다음과 같다.

```
N개는 실패했고, 성공(통과)한 테스트는 0개다
```

- `N`은 `not implemented`로 실패한 테스트 수다. 숫자는 `npx vitest run` 결과에서 가져오며 추측하지 않는다.
- Red가 맞을 때: 위 문장 그대로 쓴다. 실패 원인이 모두 `not implemented`이면 `(전부 not implemented)`를 덧붙인다.
- Red가 아닐 때: 같은 형식으로 실제 숫자를 쓰고 문제를 드러낸다. 예: `7개는 실패했고, 성공(통과)한 테스트는 2개다 (Red 아님)`, `Broken 3개 (not implemented 아님)`.

요약 줄 앞에는 아래를 짧게 보고한다.

- 만든 파일 목록(테스트, 구현 껍데기)
- Broken을 고쳤다면 무엇을 고쳤는지

커밋은 사용자가 요청할 때만 한다.
