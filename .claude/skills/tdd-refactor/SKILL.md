# tdd-refactor

`tdd-green` 다음의 Refactor 단계다. **동작은 바꾸지 않고 구조만** 개선한다.

시작 전에 `npx vitest run`을 한 번 돌린다. 실패하는 테스트가 있으면 리팩터링하지 않고 "먼저 tdd-green으로 테스트를 통과시켜야 한다"고 알린 뒤 끝낸다. 통과 수를 기록해 둔다(기준선).

## 규칙

- 동작을 바꾸지 않는다. 기능 추가, 버그 수정, 문구 변경은 리팩터링이 아니다. 발견하면 고치지 말고 보고에 적는다.
- 테스트 파일은 고치지 않는다. 테스트를 고쳐야만 통과하는 변경은 동작이 바뀐 것이다.
- 한 번에 **하나만** 고친다. 여러 개선을 한꺼번에 하지 않는다.
- 범위는 대상 기능과 관련된 파일로 한정한다. 무관한 파일(예: 미추적 파일)이나 사용자의 다른 미커밋 변경은 건드리지 않는다.

## 점검 기준 (5개)

대상 코드를 읽고 아래 5가지를 차례로 점검한다.

1. **중복**: 같거나 거의 같은 코드가 둘 이상 있는가. 함수나 상수로 합친다.
2. **이름**: 변수, 함수, 파일 이름이 역할을 말해 주는가. `handle` 시작 규칙과 파일 이름 규칙도 여기서 본다.
3. **한 함수가 너무 많은 일**: 한 함수가 검증, 상태 변경, 저장, 표시를 섞어 하는가. 역할별로 나눈다.
4. **매직넘버**: 의미를 알 수 없는 숫자나 문자열 리터럴(저장 키, 길이 제한 등)이 있는가. 이름 있는 상수로 바꾼다. UI 문구는 대상이 아니다.
5. **CLAUDE.md 규칙 위반**: 컴포넌트 named export(`App`은 예외), 이벤트 함수 `handle` 시작, 파일 이름 규칙, 테스트 파일 위치, 파일 200줄 이하.

점검 결과로 개선 후보 목록을 만들어 사용자에게 한 줄씩 보여 준다(어느 기준, 어디, 무엇을). 후보가 없으면 "개선할 것 없음"으로 끝낸다.

## 반복 절차

### 1. 후보 하나 고르기

위험이 낮고 효과가 분명한 것부터(규칙 위반 → 이름 → 매직넘버 → 중복 → 함수 분리) 하나만 고른다. 어떤 기준의 무엇인지 한 줄로 밝힌다.

### 2. 변경

고른 것만 바꾼다. **바꾼 파일과 이전 내용을 기억해 둔다.** 되돌릴 때 필요하다.

### 3. 매번 테스트 실행

`npm test`는 watch 모드라 끝나지 않으므로 한 번만 도는 명령을 쓴다.

```
npx vitest run
```

- **전부 통과하고 통과 수가 기준선과 같다**: 성공이다. 한 줄로 알리고 1번으로 돌아간다.
- **하나라도 깨지거나 통과 수가 줄었다**: 방금 변경을 **즉시 되돌린다.** 되돌리는 범위는 이번 단계에서 바꾼 부분뿐이다. 사용자의 다른 변경을 건드리는 `git checkout .`, `git reset --hard` 같은 명령은 쓰지 않는다. 되돌린 뒤 `npx vitest run`으로 기준선으로 돌아왔는지 확인하고, 그 후보는 "포기"로 기록한다. 같은 후보를 다시 시도하지 않는다.

타입이나 린트가 걸리는 변경이면 `npm run build`와 `npm run lint`도 돌려 확인한다. 깨지면 같은 방식으로 되돌린다.

### 4. 후보가 없을 때까지 반복

후보를 모두 처리하면 끝낸다.

## 보고

마지막에 전후 비교를 요약한다.

```
## 리팩터링 요약

| # | 기준 | 변경 | 결과 |
|---|------|------|------|
| 1 | 매직넘버 | `App.tsx` 저장 키 `'memos'` → `STORAGE_KEY` | 적용 |
| 2 | 중복 | ... | 되돌림 (테스트 N개 실패) |

- 변경 파일: ...
- 줄 수: 전 N → 후 M (파일별로 큰 변화만)
- 테스트: 전 통과 a → 후 통과 a, 실패 0
- 동작 변경: 없음
- 보고만 하고 고치지 않은 것: (버그나 기능 제안이 있으면)
```

전후 비교에는 가능하면 바뀐 부분의 짧은 코드 전/후를 한두 개 보여 준다. 커밋은 사용자가 요청할 때만 한다.
